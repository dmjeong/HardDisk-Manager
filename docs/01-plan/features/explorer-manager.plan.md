# Explorer Manager 개발 계획

작성일: 2026-10-21 · 버전: 0.1 · 상태: 계획안 작성 완료, 운영 조건 확인 전

Explorer Manager는 여러 드라이브의 사용량을 감시하고, 설정된 용량 기준을 넘으면 보관 기간이 지난 데이터를 오래된 순서로 삭제하는 Windows 상주 프로그램이다. 삭제 내역, 복구 가능 여부, 자원 사용량과 디스크 이상을 한 화면에서 확인한다.

구현 기준은 **WPF, .NET Framework 4.8, x64, MVVM**이다. Windows Service가 정책 실행과 이력을 담당하고, 사용자 세션의 WPF 앱이 설정·알람·복구를 담당한다. 상세 구조와 처리 순서는 [기술 설계안](../../02-design/features/explorer-manager.design.md)에 정의한다.

## 1. 확정 요구사항과 기본 가정

사용자가 지정한 플랫폼과 기능은 요구사항으로 유지한다. 아래 운영 값은 답변 전까지 사용하는 설계 기본값이며, 실제 운영값으로 승인된 것은 아니다.

|---|---|---|

| 개발 대상 | .NET Framework 4.8 대상 빌드 | 최신 Windows의 4.8.1 런타임에서도 검증 |

| 캐시 초과 | 이전 복구본부터 퇴출, 단일 파일이 캐시보다 크면 스킵 | 큰 파일의 영구 삭제 또는 별도 저장 허용 여부 |
| 초기 실행 | 삭제 미리보기, 정책별 자동 삭제는 명시적으로 활성화 | 운영 담당자와 권한 |

## 2. 요구사항과 완료 기준

| ID | 기능 | 구현 범위와 완료 기준 |
|---|---|---|
| R01 | N개 드라이브 관리 | 볼륨 식별자로 등록하고 드라이브 문자가 바뀌어도 다른 디스크를 오인하지 않는다. 드라이브별 정책·상태·일시정지를 제공한다. |
| R02 | 용량과 기간을 결합한 삭제 | 용량 기준 충족과 보관 기간 만료를 모두 만족해야 삭제한다. 최근 파일과 제외 경로는 삭제하지 않는다. |
| R03 | 오래된 순서와 목표 도달 중단 | 같은 볼륨의 관리 폴더 전체 후보를 정렬한다. 매 항목 전후 실제 여유 공간을 측정하여 목표 도달 후 다음 삭제를 시작하지 않는다. |
| R04 | 백그라운드 실행 | 부팅 후 서비스가 실행되고, UI 종료·사용자 로그아웃 뒤에도 자동 작업이 지속된다. |
| R05 | 자원 모니터링 | CPU 사용률·온도, RAM, 볼륨 사용량, 물리 디스크 읽기/쓰기 처리량·지연·큐를 표시한다. 지원하지 않는 센서는 N/A와 원인을 표시한다. |
| R06 | 삭제 이력 | 경로, 삭제 파일 수, 실제 삭제 폴더 수, 논리 바이트, 전후 여유 공간, 스킵·실패 사유, 정책 버전, 실행 주체를 남긴다. |
| R07 | 잠긴 파일 처리 | 다른 항목 처리를 계속하며 잠금 알람과 로그를 남긴다. 권한 오류와 잠금 오류를 구분한다. |
| R08 | 강제 종료 확인 | 알람에 “강제 종료 후 삭제하시겠습니까?”를 표시한다. 허용된 사용자 앱만 명시적 승인 후 종료하고, 파일 조건을 재검증하여 재시도한다. |
| R09 | 1GB 임시 복구 | 삭제 전 원본을 캐시에 저장·검증한다. 캐시가 남아 있는 파일의 내용과 지원 메타데이터를 복구한다. 초과·퇴출·재시작 한계를 표시한다. |
| R10 | HDD 이상 로깅 | 부하가 있는 상황의 지속 지연, 읽기/쓰기 오류, 지원 장치의 건강 상태 변화를 기록하고 알람을 제공한다. |
| R11 | MVVM 준수 | View와 ViewModel에서 파일 삭제·DB·센서·프로세스 종료를 직접 실행하지 않는다. 의존성 규칙을 자동 검사한다. |
| R12 | 운영 기능 | 미리보기, 제외 경로, 동시 실행 제어, 긴급 정지, 이력 조회·내보내기, 설정 검증, 서비스 상태와 장애 복구를 제공한다. |

R05와 R10의 온도·건강 정보는 해당 PC에서 센서가 실제로 제공하는 항목에 한해 검증한다. 지원 가능한 항목은 1주차에 장비별 표로 확정한다.

## 3. 핵심 동작 결정

### 3.1 삭제 정책

볼륨 용량을 `T`, 실제 여유 공간을 `F`라 하면 사용률은 `100 × (T − F) / T`이다. 예를 들어 90% 이상이면 정리를 시작하고 85% 이하가 되면 멈춘다. 시작과 중단 기준을 다르게 두어 경계에서 작업이 반복되는 현상을 줄인다.

보관 기간 30일은 작업 시작 시각 UTC에서 30×24시간을 뺀 시각보다 마지막 수정 시각이 오래된 파일을 뜻한다. “지난달 폴더”처럼 달력 기준이 필요하면 별도 정책으로 정의한다. 사용량이 높아도 보관 기간이 남은 파일까지 자동으로 삭제하지 않는다.

목표에 미달한 채 후보가 소진되면 `대상 부족`, 잠금이나 큰 파일 때문에 진행할 수 없으면 원인별 수치와 함께 `부분 완료`로 종료한다. 정책을 임의로 완화하지 않는다.

### 3.2 폴더 삭제

폴더의 날짜만으로 하위 내용을 일괄 삭제하지 않는다. 파일을 개별 판단하고 빈 폴더만 제거한다. 등록 루트 자체는 삭제하지 않는다. 빈 폴더도 기간·제외 조건을 검사하며, 목표 용량에 도달하면 남아 있는 빈 폴더 삭제도 중단한다.

날짜별 폴더를 통째로 삭제해야 하는 업무는 후속 결정 사항이다. 폴더 단위 원자성과 파일 단위 즉시 중단은 충돌할 수 있어 별도의 정책 의미가 필요하다.

### 3.3 복구 가능 범위

삭제 후 원본 내용을 다시 읽을 수는 없으므로 **RAM 복사 → 검증 → 삭제** 순서로 구현한다. 캐시는 최근 삭제 항목을 유지하는 전역 FIFO 방식이다. 큰 작업으로 여러 GB를 삭제해도 모든 파일을 복구할 수 있는 것은 아니다.

기본안에서는 캐시에 온전히 담을 수 없는 단일 파일을 스킵한다. 기존 복구본은 새 복구본이 들어오면서 퇴출될 수 있으며, 서비스 종료·재시작·전원 종료 시 캐시가 사라진다. WPF 창만 닫는 경우에는 서비스의 캐시가 유지된다.

1GiB는 복구 캐시 예산이다. 프로그램 전체 메모리는 런타임·UI·DB 비용 때문에 이보다 크다. 일반적인 프로세스 메모리는 OS 페이지 파일에 기록될 수 있으므로, “프로그램이 복구 파일을 디스크에 저장하지 않는다”와 “물리 RAM에만 존재한다”를 구분한다. 엄격한 물리 RAM 전용이 필요하면 별도 설계와 장비 검증이 필요하다. [Microsoft VirtualLock 설명](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtuallock)

### 3.4 잠금과 강제 종료

파일 잠금으로 실패하면 즉시 스킵하고 알람을 남긴다. 알람에는 파일 경로, 관련 프로세스, 복구 가능 여부, 종료 시 저장하지 않은 작업이 사라질 수 있다는 안내를 표시한다. 기본 선택은 `건너뛰기`이다.

운영체제 필수 프로세스, 서비스, 보호 프로세스, 다른 사용자 세션의 프로세스는 v1의 강제 종료 대상에서 제외한다. 식별이나 권한 확인이 불가능하면 종료하지 않는다. 사용자가 없는 경우 알람을 보관하고 자동 강제 종료하지 않는다.

### 3.5 삭제 용량과 확보 용량

삭제한 파일의 논리 크기 합계와 실제 디스크 여유 공간 변화는 별도로 기록한다. 다른 프로그램의 동시 쓰기, 파일 시스템 할당 단위, 삭제 완료 지연 때문에 두 수치가 일치하지 않을 수 있다. 목표 도달 여부는 논리 크기 합계가 아니라 OS에서 다시 읽은 여유 공간으로 결정한다.

## 4. 구조와 기술 선택

| 구성 | 책임 | 선택안 |
|---|---|---|
| WPF 앱 | 대시보드, 정책, 이력, 복구, 알람, 트레이 | WPF + MVVM, .NET Framework 4.8 x64 |
| Windows Service | 스케줄, 삭제, RAM 캐시, 이력, 상태 관리 | ServiceBase 기반, UI와 독립 실행 |
| 세션 내 종료 어댑터 | 승인한 사용자 앱 종료 | WPF 프로세스의 UI 외부 서비스 계층 |
| 센서 어댑터 | 사용률·온도·디스크 상태 수집 | Windows PDH/WMI + LibreHardwareMonitor 후보 |
| 선택적 센서 호스트 | 센서 오류·권한 요구 분리 | 장비 PoC 결과에 따라 별도 프로세스 |
| 프로세스 간 통신 | 명령, 조회, 상태 이벤트 | 로컬 Named Pipe, ACL과 사용자 인증 |
| 영구 데이터 | 정책·이력·알람·후보 목록 | SQLite, 서비스만 쓰기 |
| 진단 로그 | 서비스/어댑터 오류 | 크기 제한 회전 로그 + Windows Event Log |

서비스는 사용자 데스크톱에 직접 UI를 표시할 수 없으므로 별도의 WPF 프로세스가 팝업을 담당한다. [Microsoft 서비스와 사용자 상호작용](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services)

LibreHardwareMonitor는 온도 수집 후보이다. .NET Framework 대상이 제공되지만 일부 센서는 관리자 권한이 필요하므로 배포 버전·드라이버·대상 장비에서 먼저 검증한다. [프로젝트 공식 설명](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor)

## 5. 1차 출시 범위

필수 기능은 R01~R12를 포함한다. 자동 삭제는 설치 직후 꺼져 있으며, 등록 경로의 미리보기 결과를 확인하고 정책을 활성화하면 이후 주기 실행은 매번 승인 없이 동작한다. 사용자가 매번 결정하는 항목은 잠금 앱의 강제 종료와 복구 충돌 처리이다.

v1은 로컬 NTFS의 일반 파일을 기준으로 한다. Reparse point, junction, symbolic link, 다중 hard link, EFS, 대체 데이터 스트림이 있는 파일, sparse/compressed 파일 등은 복구 및 경로 안전성을 검증하기 전까지 스킵 사유를 표시한다. 숨김·시스템·읽기 전용 파일과 OS·프로그램·사용자 프로필 루트는 기본 보호 대상이다.

후속 범위는 NAS/UNC, 외장 드라이브 자동 정리, ReFS, RAID/Storage Spaces의 세부 물리 디스크 진단, 디스크 격리 보관, 재부팅 후 복구, 날짜 폴더 단위 삭제, 원격 중앙 관리이다. 기존 요구사항에서 제외한 기능이 아니라 운영 환경에 따라 확정할 확장 항목이다.

## 6. 개발 단계와 일정

Windows 데스크톱 개발자 1명, 실제 운영 장비 접근 가능, v1 기본 범위를 가정한 **8주 개발 + 1~2주 현장 조정 여유**의 추정이다. 센서 드라이버 승인, NAS, 엄격한 물리 RAM 요구가 추가되면 재산정한다.

| 단계 | 기간 | 작업과 산출물 | 완료 조건 |
|---|---|---|---|
| P0 기술 검증 | 1주차 | OS/디스크/센서 목록, Service↔WPF 통신, 배타 핸들 복사·삭제, RAM 예산, 잠금 프로세스 탐지 PoC | 실제 장비에서 가능한 기능과 미지원 항목 확정 |
| P1 기반 구조 | 2주차 | 솔루션 계층, MVVM 기본, 서비스 수명주기, Pipe 권한, SQLite와 설정 버전 | UI 없이 서비스 실행, UI 재연결, 권한별 명령 검증 |
| P2 삭제·복구 핵심 | 3~4주차 | 볼륨 식별, 전체 후보 정렬, 기간·용량 정책, 삭제 저널, 1GiB 캐시, 복구 | 오래된 순서·중단·경합·복구 해시 테스트 통과 |
| P3 잠금·알람 | 5주차 | 잠금 스킵, 알람 큐, 승인 티켓, 세션 내 앱 종료, 중복 알람 억제 | 승인 없는 종료 0건, PID 재사용과 지연 승인 재검증 |
| P4 모니터링 | 6주차 | CPU/RAM/디스크 성능, 지원 온도·건강 정보, 이상 규칙, 그래프 | 유휴·부하·장치 분리·센서 오류 시 상태 정확성 |
| P5 화면·운영 통합 | 7주차 | 정책 편집, 미리보기, 이력/CSV, 복구센터, 설치·업데이트, 로그 제한 | 주요 사용자 흐름과 서비스 운영 점검 통과 |
| P6 종합 검증 | 8주차 | 100만 파일/16볼륨 검증 환경, 72시간 연속 실행, 장애 주입, 현장 시범 | 아래 인수 기준 충족, 운영 매뉴얼 완성 |
| 현장 보정 | 추가 1~2주 | 장비별 센서, 디스크 부하, 업무 보관 정책 조정 | 미지원·제약 목록과 최종 운영 설정 확정 |

WPF 화면은 P1부터 기능별로 연결하고 P5에서 운영 흐름을 완성한다. P0에서 핵심 위험이 해결되지 않으면 해당 항목의 대안을 결정한 뒤 후속 구현 범위를 고정한다.

## 7. 품질 목표와 검증

수치는 실측 결과가 아니라 개발 목표다. 성능 기준 장비는 P0에서 모델·CPU·RAM·디스크 구성과 데이터셋을 기록하여 고정한다.

| 검증 항목 | 인수 기준 |
|---|---|
| 삭제 정확성 | 보호·기간 미도달·경로 이탈·변경된 파일 삭제 0건 |
| 삭제 순서 | 스냅샷 내 실행 가능한 후보가 볼륨 전체에서 시각 오름차순 처리됨 |
| 용량 중단 | 매 삭제 전후 재측정, 목표 달성 후 다음 항목 삭제 0건 |
| 일부 실패 | 잠금·접근 거부·대상 부족이 있어도 다른 정상 후보 처리, 이유별 기록 |
| 복구 정확성 | 캐시 생존 항목의 본문 SHA-256 일치, 지원 메타데이터 복원, 기존 파일 덮어쓰기 0건 |
| 캐시 한도 | 준비·삭제 대기·복구 중인 데이터까지 합산한 캐시 관리 할당 1GiB 이하 |
| 이력 일관성 | 실제 성공·실패·불확정 상태 구분, 폴더 합계 중복 집계 0건 |
| 중단과 장애 | UI 종료와 로그아웃에도 서비스 유지, 저널 기록 불가 시 신규 삭제 중단 |
| UI 응답 | 100만 행 전체 로딩 없이 페이지 조회, 일반 조작 응답 200ms 이내 목표 |
| 정상 대기 부하 | UI 최소화·캐시 비움 기준 전체 CPU 평균 1% 이하, 서비스와 UI 기본 메모리 합계 250MiB 이하 목표; 센서 호스트 비용 별도 측정 |
| 정리 부하 | 복구본 읽기 기본 10MiB/s 상한 제안, 메타데이터 스캔 속도와 작업 동시성 조절 |
| 연속 운전 | 72시간 동안 캐시 정상 증가를 제외한 메모리·핸들 수의 지속 증가 없음 |
| 보안·권한 | 허용하지 않은 로컬 사용자 및 원격 Pipe 연결의 변경 명령 거부 |

가상 디스크/VHDX는 볼륨 정책 검증에 사용하고, 온도·SMART·실제 I/O 이상은 물리 HDD/SSD에서 별도로 확인한다. 개발 데이터로만 삭제 시험을 수행한다.

## 8. 주요 위험과 대응

| 위험 | 영향 | 설계 대응 |
|---|---|---|
| 경로 설정 실수 또는 링크 경유 | 의도하지 않은 파일 삭제 | 등록 루트 제한, 보호 경로, reparse 제외, 파일 ID와 최종 경로 재검증 |
| 스캔 후 파일이 바뀜 | 최신 파일 삭제·잘못된 복구 | 삭제 직전 배타 핸들 확보와 메타데이터 재확인, 동일 핸들 복사·삭제 |
| 캐시 퇴출·서비스 재시작 | 삭제 파일 복구 불가 | 복구 가능 상태를 실시간 표시, 종료·업데이트 안내, 영구 복구와 구분 |
| 대용량 파일 위주 환경 | 1GiB 캐시 정책으로 목표 달성 불가 | 스킵 예상량을 미리보기로 제시, 영구 삭제/디스크 보관 정책 별도 결정 |
| 프로그램 강제 종료 | 사용자의 미저장 작업 손실 | 건별 승인, 대상 식별, 세션·권한 확인, 보호 프로세스 제외 |
| 센서 미지원·드라이버 차단 | 온도·건강 정보 누락 | capability 상태와 사유 표시, 어댑터 분리, 실제 장비 PoC |
| 로그 디스크 가득 참 | 이력 없는 삭제 | 감사 로그 저장을 삭제 선행 조건으로 지정, 보관량 제한 |
| 외부 프로그램의 지속 쓰기 | 삭제해도 여유 공간 증가 없음 | 관측 변화 별도 기록, 배치 시간/삭제량 상한, 원인 알람 |
| 비정상 디스크에 추가 부하 | 장애 악화 | 건강 위험 신호 시 해당 디스크 자동 정리 중단, 별도 점검 요청 |

## 9. 확인할 운영 조건

아래 항목은 계획을 작성하는 데에는 기본 가정을 적용했으며, 실제 운영 삭제를 활성화하기 전에 확정한다.

1. 대상 OS와 로컬 HDD/SSD·USB·NAS 포함 여부, 볼륨 수와 파일 수.
2. 보관 기간의 기준: 수정 시각, 생성 시각, 폴더명 날짜 또는 업무 데이터.
3. 1GB의 단위, 파일 크기 분포, 캐시 초과 파일의 스킵/영구 삭제/디스크 보관 선택.
4. 날짜별 폴더를 통째로 보존·삭제해야 하는지, 파일별 처리가 가능한지.
5. 사용량 개시·중단값, 점검 주기, 야간 작업 시간대, 1회 삭제량 상한.
6. CPU·메인보드·스토리지 모델, 센서용 드라이버 설치 허용 여부.
7. 강제 종료를 허용할 업무 프로그램, 운영자 계정과 다중 로그인 사용 여부.
8. 이력 보관 기간과 최대 크기, 복구본을 재부팅 뒤에도 유지해야 하는지.

## 10. 구현 시작 순서

첫 구현은 Windows 검증 환경에서 P0를 수행한다. 특히 배타 핸들 기반 복사·삭제, 실제 여유 공간 변화, 서비스와 사용자 세션의 알람, 대상 장비의 온도 센서를 먼저 확인한다. 이후 계층과 인터페이스를 고정하고 삭제 엔진·캐시·감사 이력을 한 흐름으로 구현한다.

계획과 설계의 작성 완료는 프로그램의 구현 완료나 실제 운영 삭제의 검증 완료를 뜻하지 않는다.
