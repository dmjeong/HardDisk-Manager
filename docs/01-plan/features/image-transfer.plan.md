# Image Transfer — 개발 계획

작성일: 2026-10-26 · 상태: FTP/FTPS 구현·Windows 검증 완료 · 최초 설계 기준 코드: `69c08c8`

## 1. 목적과 확정 범위

지정된 로컬 경로의 이미지를 기존 상위 서버에 백그라운드로 업로드한다. 사용자는 **TCP 또는 FTP**, 그리고 **상위 수신 프로그램을 변경할 수 없고 파일만 올리는 기능**이라고 확정했다. 새로운 수신 API, 서버 에이전트, 자체 ACK 규격을 요구하지 않는다.

**FTP/FTPS adapter와 WPF Transfers를 구현했다.** TCP는 기존 수신 명세를 확보했을 때 해당 규격으로 구현한다. WPF / .NET Framework 4.8 / x64 / C# 7.3 / MVVM을 유지한다. [상세 기술 설계](../../02-design/features/image-transfer.design.md)의 구현 확정 사항과 [검증 결과](../../03-analysis/image-transfer.analysis.md)를 함께 확인한다. 실제 운영 서버의 주소·계정·수신 규칙은 제공되지 않아 시험 서버와 Windows CI로 검증한다.

## 2. 기본값과 미확정 사항

| 항목 | 설계 기준 |
|---|---|
| 서버 | 수정 불가, 기존 FTP/FTPS 또는 기존 TCP 규격 사용 |
| 전송 시점 | 별도 응답 전 제안: 저장 완료 후 자동 감지 + 주기 재검색 + 수동 실행 |
| 기존 이미지 | Preview로 범위 선택 후 backfill |
| 대상 | 로컬 NTFS, 하위 폴더 포함, 원본 이미지 그대로 전송 |
| 삭제 연동 | 제안 기본값 `RequireVerifiedUpload`, 기존 기간·용량·RAM 복구 조건 유지 |
| 미확정 | 주소/계정/원격 경로, 파일명 규칙, 임시 경로 감시 여부, 즉시 소비 여부 |
| 미확정 | 서버의 읽기/hash/rename/resume 지원, 이미지 형식·크기·발생량 |

## 3. 설계 원칙

1. 전송 중 / FTP 완료 응답 / 원격 내용 검증 / 상위 업무 처리를 구분한다. 업무 처리는 기존 증빙이 없으면 확인 불가다.
2. SQLite 대기열로 재시작 후 복구한다. FTP에는 범용 멱등성 API가 없으므로 결과 불명을 무조건 재업로드하지 않는다.
3. 기존 파일명·감시 규칙을 유지한다. 수신기가 보지 않는 임시 위치에 업로드하고 검증 후 rename하는 방식을 우선하되 실제 호환성을 확인한다.
4. 서버 SHA-256 또는 read-back 검증과 크기 검사만 한 상태를 구분한다.
5. 삭제 직전 현재 원본 SHA-256과 전송 증빙을 비교한다. Pause·정책 변경·대기열 포화·DB 오류로 보호가 풀리지 않는다.
6. 업로드는 고정 버퍼 스트리밍이며 RAM 복구 캐시는 사용하지 않는다. 큰 이미지의 전송 가능 여부와 삭제 가능 여부는 별개다.
7. 외부 프로그램이 원본을 덮어쓰거나 지우면 이전 버전을 대기열만으로 보장할 수 없다. 저장 완료 후 원본 불변을 우선한다.
8. 용량 목표 도달 시 현재 폴더 완료 후 중단하는 기존 동작을 유지하고, 미전송 파일은 폴더 완료 대상에서 제외하여 남긴다.

## 4. 기능과 완료 판정

| ID | 기능 | 완료 판정 |
|---|---|---|
| IT-01 | 서버/경로 설정 | 연결·권한·capability 확인, 범위/경로 충돌 검출 |
| IT-02 | 안정화와 감지 | 쓰기 중 보호, 완료 신호 활용, 중복·누락·폴더 이동 재검색 |
| IT-03 | 영속 대기열 | 작업/시도/증빙/lease가 재시작 후 복구 |
| IT-04 | FTP 전송 | binary/passive, 임시 업로드, 지원 시 검증된 resume, rename |
| IT-05 | 검증/충돌 | 해시/크기 수준 구분, 덮어쓰기 기본 금지, 결과 불명 보류 |
| IT-06 | 정리 연동 | 미발견 대상 보호, 최종 해시 비교, 정책 변경 경합 제어 |
| IT-07 | 부하/Interlock | 디스크별 조정, 대역폭·동시성·RAM 제한, 장애 backoff |
| IT-08 | MVVM/감사 | Transfers 화면, 정책 편집, 이력·알람·자격 증명 분리 |
| IT-09 | TCP 확장 | 기존 명세 확보 시 그 framing/ACK/재전송 규칙 구현 |

한 route는 한 상위 대상이며 원본 범위가 겹치는 route는 첫 버전에서 금지한다. 이미지 변환, 원격 복구, 서버 원격 제어, 새 수신 프로그램, NAS 원본, 다중 서버 복제는 범위 밖이다.

## 5. 개발 순서

| 단계 | 작업 | 통과 조건 |
|---|---|---|
| 0 | 실제 서버 호환성 조사 | 경로/명명/감시/검증 권한/응답 의미 확정 |
| 1 | 스캔 제한 보완·DB migration·보호 모델 | 단일 대형 폴더 제한 준수, 기존 동작 회귀 없음 |
| 2 | 탐색·안정화·대기열 | 누락/중복/재시작 복구, 메모리 상한 |
| 3 | FTP adapter와 서버 fixture | 전송/resume/검증/rename/충돌/응답 유실 시험 |
| 4 | 삭제 최종 gate | 미전송·내용 변경·결과 불명·DB 장애에서 삭제 0건 |
| 5 | 부하·스케줄·알람 | 같은 HDD 읽기 조정, 작업 공정성 |
| 6 | MVVM 화면/운영 설정 | 편집 보존, pagination, 권한/입력 검증 |
| 7 | 장애 주입·실장비·배포 | Windows 회귀, 실제 수신기 호환, 72시간 시험 |

TCP만 제공하면 단계 3을 기존 TCP 명세용 adapter로 대체한다. 전송은 Disabled로 배포하고 연결 확인 → 소규모 Preview/호환성 시험 → 기존 파일 범위 선택 → 자동 전송 활성화 순서로 운영한다. 서버 정보와 파일 발생량 확인 후 일정을 산정한다.

## 6. 위험과 대응

| 위험 | 대응 |
|---|---|
| 생산 중 파일/같은 이름 덮어쓰기 | 완료 신호·읽기 lease·파일 세대·SHA-256 |
| rename 응답 유실 뒤 서버가 파일 소비 | `PublicationUnknown`, 확인 수단 없으면 자동 재전송/삭제 보류 |
| 원격 경로 충돌 | Hold, 단독 작성 namespace, 기존 수신기 파일명 규칙 확인 |
| 임시 파일을 수신기가 처리 | 감시 밖 staging 또는 기존 임시 이름 규칙 활용 |
| 기능/권한 부족 | 검증 수준 표시, 약한 검증을 강한 성공으로 표시하지 않음 |
| 장애 동안 로컬 공간 부족 | 미전송 보호, backlog·잔여 시간·용량 경고 |
| DB/서비스 장애·이력 정리 | durable queue, fencing, FULL 동기화, 필요한 증빙 보존 |
| HDD/네트워크 부하 | 스트리밍·속도 제한·물리 디스크별 조정·실측 |

## 7. 최종 완료 기준

- 변경할 수 없는 실제 상위 서버의 규칙에 맞게 업로드한다.
- 결과 불명은 보류하고, 로컬·원격 상태를 확인한 뒤 재시도한다.
- `RequireVerifiedUpload`에서 미전송/전송 중/결과 불명/현재 내용 불일치 파일 삭제는 0건이다.
- 바이트 수, FTP 완료 응답, 원격 검증 방법, 게시 경로/시각을 추적한다.
- 기존 복구·폴더 완료 후 중단·Interlock·강제 종료 승인 동작을 유지한다.
- .NET 8 SDK 없이 Framework 4.8 빌드·서비스·WPF 회귀 시험을 통과한다.
- 실제 HDD에서 처리량, 생산 프로그램 영향, 장애 후 backlog 해소와 장시간 리소스를 측정한다.

실제 운영 서버 인수 시 상세 설계의 호환성 표를 접속 정보와 수신 규칙으로 채우고 소규모 업로드부터 확인한다. 시험 서버의 자동 검증과 실제 장비의 호환성·처리량 검증은 별도로 기록한다.
